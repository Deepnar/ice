# ICE Post-Paper Roadmap

> Living checklist of everything queued after the paper. Distilled from [rough_post_paper_work.md](rough_post_paper_work.md) (raw notes — keep that file as the source of nuance), the experiment reports in `experiments/*/results*`, and the paper's limitations section.
>
> **How to use this file:**
> - **Work it in order** (Phase 0 → Track A → B → …), respecting dependencies. The ordering is deliberate.
> - **Build up, never replace.** Each item must be implemented so that *later* items build on top of it, not tear it out. Concrete example: the decay / background-worker scheduling fixes (C7) are later absorbed by the agentic Memory Maintenance Agent (Track D) — so do C7 with clean, composable worker interfaces the agent can later orchestrate, not a throwaway patch. When implementing any item, check what downstream items depend on it and design for that end-state.
> - **No first versions — build the robust, considered version.** "Perfect" is impossible, but every feature is implemented as the durable, thought-through version, not a quick MVP to be redone later: handle the edge cases, use the proper algorithm/structure (not a toy stand-in), and design for the end-state. If the proper version is too big for one pass, split it into robust sub-items — never ship a knowingly-throwaway version.
> - **Look ahead before building (mandatory pre-step).** Before implementing ANY item, scan the rest of the roadmap for later items in the **same realm/subsystem**. If a later item will rework the same area: (a) design the current implementation to be forward-compatible with where that item is heading (pick the primitive the future item needs — e.g. A5 filters on a *batch-id set* because C6's cross-chat/session/@-mention scoping all resolve to that same set); or (b) if they genuinely conflict and can't be reconciled, decide explicitly and record it — do the later item first, or note the exact seam that will need changing. Never implement in a way a *known* future item will have to tear out. State the look-ahead result in the item's completion note.
> - **Propagate on completion — refresh downstream stale references (mandatory post-step).** The mirror of look-ahead. After finishing an item, scan the still-unchecked items for any that describe the *old* behavior of what you just changed, and update them to the new reality (note the new dependency / what's now already done). A completed feature that leaves later items describing the pre-change world will silently mislead a future session (e.g. after A6, item D1 no longer "replaces the pipeline"; after A7, F3's graph view must render typed nodes + backlinks + negations). Only mark an item `[x]` after this pass.
> - **Earn the checkmark.** Only `[x]` an item after its full *original* scope is implemented **and** behaviorally validated (a real run/test, not just a syntax check) — audit against the entry text, not memory of it. If part is genuinely deferred, say so explicitly in the note rather than checking it off.
> - Each entry is *intent + rationale*, **not a spec**. When an item's turn comes, the concrete design gets discussed in-session first; only then is it implemented.
> - Check off `[x]` when done. On completion, update [ICE_Architecture.md](ICE_Architecture.md): new systems get a new section, reworked systems get their existing section edited.
> - Phase 0 decisions may kill, reshape, or re-home items below (some conversational features may move to the Coding side). That is expected.
> - **⚑ REMEMBER THE END-STATE (full statement in the Track F preamble — easy to forget, don't):** `./ice`, `./stop_ice`, and `setup.sh` are **dev scaffolding, destined for replacement** by one packaged frontend+backend app that boots the whole stack itself — and **ICE-as-MCP (E7) additionally needs its own SEPARATE headless boot story** (no frontend open at all; still to be designed). Any item that touches startup, services, or the stack (`./ice`, workers, docker, model servers) must be written and built knowing both of those destinations.
>
> > **Corrections (verified in code, 2026-07) — the paper's limitations section repeats two claims that are false in the actual code; fix before arXiv:**
> 1. **NER was loaded, not regex-fallback.** [ner_utils.py](../src/retrieval/ner_utils.py) loads `models/ner/ner_model.pt` (present on disk) and only regex-falls-back if that file is missing. NER was active during the experiments (empirically ~95% recall). Codex's weak numbers come from other handicaps, **not** entity detection.
> 2. **No "corroboration trap" starving retrieval.** Codex retrieval filters only on `valid_until == None` (time-validity) in `_traverse_graph`, MERA, and context_payload regeneration — **none filter `confidence == 'active'`**. So `pending` (single-extraction) edges *are* traversed and injected; `confidence=='active'` only gated a coarse 1.5× score boost. The claim that pending edges never contribute to retrieval is false. The real Codex weaknesses are chunk size (A1), entity-vs-relation retrieval (A4), leg under-representation (A10), and an inert confidence signal with no reinforcement (A3, now fixed).

## Track E — Coding ICE / Project State Engine

> **North star (settled in-session 2026-07): kill the persistence tax.** What makes an AI agent productive on a long-lived project today is a *human* who hand-maintains a CLAUDE.md, an architecture doc, and a roadmap — with discipline almost nobody has time for. Coding ICE exists to BE that discipline automatically: the persistent, always-current **context authority** for a codebase, consulted **inside the agent's loop at every step** (not just session start), so the model stops wasting turns re-exploring, reading the wrong files, and re-deriving old decisions. (Evidence this matters even with good scaffolding: mid-session, with CLAUDE.md pointing at the roadmap, the assistant still read VISION.md + rough notes instead — in-loop steering can't rely on model discipline; the system must serve the right pointer at the right moment.)
>
> **Architecture decisions (settled 2026-07 — these supersede older framings in the entries below wherever they conflict):**
> 1. **Brain, not body — MCP-first, no own harness.** ICE does NOT become an agentic coding harness (that's months of rebuilding Claude Code badly before the memory features — the actual point — even start). ICE is a **local MCP memory/context server** that any existing harness (Claude Code, Cursor, Cline, …) mounts. The harness does file I/O, editing, looping, tests; ICE answers *what matters, where it is, why it's that way*. **E5 is thereby RESOLVED** — no Aider adapter, no own executor. A *thin dispatcher* that hard-forces "consult ICE before each step" is a recorded contingency ONLY if pull-discipline (tool descriptions + a skill/system-prompt rule) proves insufficient in real use.
> 2. **"Where, not what."** ICE serves **pointers + rationale** — `symbol → file:line`, edges, decisions, typed notes — never code bodies. The harness's own tools read the actual lines. Pointers survive edits; injected source goes stale instantly and burns budget. The code graph stores structure, never source text.
> 3. **One memory substrate; coding is an overlay.** Conversational memory (episodic/codex/procedural/slots) is not "the other mode" — it is the **rationale layer** of coding memory: the *why* lives in conversations about the code and is never in the code itself. Coding mode = conversational base + structural overlay (code graph) + code-aware serving (pointers) + git-as-timeline + the MCP tool surface. There is no conversational/coding boundary to police — that boundary was the convolution.
> 4. **Four-layer memory model for a codebase:** **Structural** (files/symbols/imports/calls — deterministic static analysis — served as pointers) · **Rationale** (decisions, rejected alternatives, the why — extracted from conversations + commits — served as typed notes) · **Temporal** (git IS the timeline; read it, don't re-store it) · **Behavioral** (conventions/patterns — procedural extraction — served as rules).
> 5. **Work-unit trigger.** "A unit of work finished → reconcile memory" is ONE concept with two signals: **git commit / task-done** in coding (semantic and precise — never guess with timers when a commit exists) and **session-gap** in conversation (C6/C7). E3/E4 fire on the former; C7's catch-up fires on the latter.
> 6. **Build vs external:** **project-specific knowledge → ICE owns it** (deterministic extractors, cheap); **world-generic knowledge → external tools fetch it** (harness WebFetch/search, doc MCPs) and ICE stores only the pointer + the project-relevant summary. We do NOT build a library-docs indexer.
> 7. **Prerequisite — the service layer (E0).** Every user-facing capability becomes an interface-agnostic service with thin adapters: REST (frontend, F1), MCP tools (E7), chat-commands (C11), workers internally. Nothing new gets built frontend-coupled again.
