# ICE Post-Paper Roadmap

> Living checklist of everything queued after the paper, and **the authoritative queue** — it is no longer a distillation of anything. It was originally distilled from the raw post-paper notes, the experiment reports in `experiments/*/results*`, and the paper's limitations section. Those raw notes have since been **fully mined** (the sweep is recorded in [BRUTAL_ASSESSMENT.md](BRUTAL_ASSESSMENT.md): every item maps to a live roadmap entry) and archived to [outdated/rough_post_paper_work.md](outdated/rough_post_paper_work.md) — read them only for historical phrasing, never as a work queue.
>
> **How to use this file:**
> - **Work it in order** (Phase 0 → Track A → B → …), respecting dependencies. The ordering is deliberate.
> - **Build up, never replace.** Each item must be implemented so that *later* items build on top of it, not tear it out. Concrete example: the decay / background-worker scheduling fixes (C7) are later absorbed by the agentic Memory Maintenance Agent (Track D) — so do C7 with clean, composable worker interfaces the agent can later orchestrate, not a throwaway patch. When implementing any item, check what downstream items depend on it and design for that end-state.
> - **No first versions — build the robust, considered version.** "Perfect" is impossible, but every feature is implemented as the durable, thought-through version, not a quick MVP to be redone later: handle the edge cases, use the proper algorithm/structure (not a toy stand-in), and design for the end-state. If the proper version is too big for one pass, split it into robust sub-items — never ship a knowingly-throwaway version.
> - **Look ahead before building (mandatory pre-step).** Before implementing ANY item, scan the rest of the roadmap for later items in the **same realm/subsystem**. If a later item will rework the same area: (a) design the current implementation to be forward-compatible with where that item is heading (pick the primitive the future item needs — e.g. A5 filters on a *batch-id set* because C6's cross-chat/session/@-mention scoping all resolve to that same set); or (b) if they genuinely conflict and can't be reconciled, decide explicitly and record it — do the later item first, or note the exact seam that will need changing. Never implement in a way a *known* future item will have to tear out. State the look-ahead result in the item's completion note.
> - **Propagate on completion — refresh downstream stale references (mandatory post-step).** The mirror of look-ahead. After finishing an item, scan the still-unchecked items for any that describe the *old* behavior of what you just changed, and update them to the new reality (note the new dependency / what's now already done). A completed feature that leaves later items describing the pre-change world will silently mislead a future session (e.g. after A6, item D1 no longer "replaces the pipeline"; after A7, F3's graph view must render typed nodes + backlinks + negations). Only mark an item `[x]` after this pass.
> - **Earn the checkmark.** Only `[x]` an item after its full *original* scope is implemented **and** behaviorally validated (a real run/test, not just a syntax check) — audit against the entry text, not memory of it. If part is genuinely deferred, say so explicitly in the note rather than checking it off.
> - **⚑ If it is WORK, it goes in an ENTRY — never in preamble prose.** Anything
>   written into a note, an inventory, an addendum or a triage block at the top of
>   this file is lost, because nobody works from the preamble. Measured 2026-08-10:
>   **[G27](#g27), [G34](#g34) and [G35](#g35) were all announced in preamble notes
>   and never given entries** — counted in the inventory, invisible to a session
>   told to do them, one of them with a decision-complete description sitting in a
>   spec the whole time. In the same sweep **[Z2](#z2) was found to have been handed
>   five pieces of work** (three by C16, one by A9b, one by the C13/C14 question)
>   recorded in a triage block its own entry did not point at. ⇒ **Open the item in
>   the same edit that announces it**, and when you hand work to a later item, write
>   it into *that item's entry*, not into the note where you noticed it.
> - **Check the ground before building on it (the other half of the checkmark rule).** Before implementing anything: verify **how the code ACTUALLY is** against what the entry claims, and **spot-check the nearby already-checked items** to confirm they are genuinely done rather than checked off optimistically. This is not paranoia — **seven consecutive entries have been wrong about their own subject** (G9 in three directions, G36 in three, and G36's own predecessors), and one of those errors would have shipped a fix for a bug that did not exist. *(Carried here from CLAUDE.md 2026-08-10, where it had been added to the same bullet and never mirrored; the CLAUDE.md shrink of `942d5a9` compared the two bullets by heading rather than by text and dropped it — which is itself the failure this rule describes.)*
> - Each entry is *intent + rationale*, **not a spec**. When an item's turn comes, the concrete design gets discussed in-session first; only then is it implemented.
> - Check off `[x]` when done. On completion, update [ICE_Architecture.md](ICE_Architecture.md): new systems get a new section, reworked systems get their existing section edited.
> - Phase 0 decisions may kill, reshape, or re-home items below (some conversational features may move to the Coding side). That is expected.
> - **⚑ REMEMBER THE END-STATE (full statement in the Track F preamble — easy to forget, don't):** `./ice`, `./stop_ice`, and `setup.sh` are **dev scaffolding, destined for replacement** by one packaged frontend+backend app that boots the whole stack itself — and **ICE-as-MCP's SEPARATE headless boot story SHIPPED with E7 (2026-07-17)**: `ice-mcp` attaches to postgres if live, else boots it via docker, then `create_core()` with the runtime-lease/standby arbitration, and lingers on shutdown (`./stop_ice` stays the full-stop path). Any item that touches startup, services, or the stack (`./ice`, workers, docker, model servers) must be written and built knowing both destinations (packaged app + headless MCP boot).
>
> > **Corrections (verified in code, 2026-07) — the paper's limitations section repeats two claims that are false in the actual code; fix before arXiv:**
> 1. **NER was loaded, not regex-fallback.** [ner_utils.py](../src/retrieval/ner_utils.py) loads `models/ner/ner_model.pt` (present on disk) and only regex-falls-back if that file is missing. NER was active during the experiments (empirically ~95% recall). Codex's weak numbers come from other handicaps, **not** entity detection.
> 2. **No "corroboration trap" starving retrieval.** Codex retrieval filters only on `valid_until == None` (time-validity) in `_traverse_graph`, MERA, and context_payload regeneration — **none filter `confidence == 'active'`**. So `pending` (single-extraction) edges *are* traversed and injected; `confidence=='active'` only gated a coarse 1.5× score boost. The claim that pending edges never contribute to retrieval is false. The real Codex weaknesses are chunk size (A1), entity-vs-relation retrieval (A4), leg under-representation (A10), and an inert confidence signal with no reinforcement (A3, now fixed).

## Track E — Coding ICE / Project State Engine

> **North star (settled in-session 2026-07): kill the persistence tax.** What makes an AI agent productive on a long-lived project today is a *human* who hand-maintains a CLAUDE.md, an architecture doc, and a roadmap — with discipline almost nobody has time for. Coding ICE exists to BE that discipline automatically: the persistent, always-current **context authority** for a codebase, consulted **inside the agent's loop at every step** (not just session start), so the model stops wasting turns re-exploring, reading the wrong files, and re-deriving old decisions. (Evidence this matters even with good scaffolding: mid-session, with CLAUDE.md pointing at the roadmap, the assistant still read VISION.md + rough notes instead — in-loop steering can't rely on model discipline; the system must serve the right pointer at the right moment.)
>
> **Architecture decisions (settled 2026-07 — these supersede older framings in the entries below wherever they conflict):**
> 1. **Brain, not body — MCP-first, no own harness.** ICE does NOT become an agentic coding harness (that's months of rebuilding Claude Code badly before the memory features — the actual point — even start). ICE is a **local MCP memory/context server** that any existing harness (Claude Code, Cursor, Cline, …) mounts. The harness does file I/O, editing, looping, tests; ICE answers *what matters, where it is, why it's that way*. **E5 is thereby RESOLVED** — no Aider adapter, no own executor. A *thin dispatcher* that hard-forces "consult ICE before each step" is a recorded contingency ONLY if pull-discipline (tool descriptions + a skill/system-prompt rule) proves insufficient in real use.
> 2. **"Where, not what."** ICE serves **pointers + rationale** — `symbol → file:line`, edges, decisions, typed notes — never code bodies. The harness's own tools read the actual lines. Pointers survive edits; injected source goes stale instantly and burns budget. The code graph stores structure, never source text.
> 3. **One memory substrate; coding is an overlay.** Conversational memory (episodic/codex/procedural/slots) is not "the other mode" — it is the **rationale layer** of coding memory: the *why* lives in conversations about the code and is never in the code itself. Coding mode = conversational base + structural overlay (code graph) + code-aware serving (pointers) + git-as-timeline + the MCP tool surface. There is no conversational/coding boundary to police — that boundary was the convolution.
> 4. **Four-layer memory model for a codebase:** **Structural** (files/symbols/imports/calls — deterministic static analysis — served as pointers) · **Rationale** (decisions, rejected alternatives, the why — extracted from conversations + commits — served as typed notes) · **Temporal** (git IS the timeline; read it, don't re-store it) · **Behavioral** (conventions/patterns — procedural extraction — served as rules).
> 5. **Work-unit trigger.** "A unit of work finished → reconcile memory" is ONE concept with two signals: **git commit / task-done** in coding (semantic and precise — never guess with timers when a commit exists) and **session-gap** in conversation (C6/C7). E3/E4 fire on the former; C7's catch-up fires on the latter.
> 6. **Build vs external:** **project-specific knowledge → ICE owns it** (deterministic extractors, cheap); **world-generic knowledge → external tools fetch it** (harness WebFetch/search, doc MCPs) and ICE stores only the pointer + the project-relevant summary. We do NOT build a library-docs indexer.
> 7. **Prerequisite — the service layer (E0).** Every user-facing capability becomes an interface-agnostic service with thin adapters: REST (frontend, F1), MCP tools (E7), chat-commands (C11), workers internally. Nothing new gets built frontend-coupled again.

- [ ] <a id="g28"></a>**G28 Style invariance — no decision may depend on HOW a thing is written** `(new — 2026-07-28, user; RUN AS PART OF Z1's COVERAGE MATRIX)` — **⚠ The user's diagnosis, and the measured reason Codex underperformed across a month of experiments.** A rule keyed on punctuation, word order, or a fixed vocabulary is a bet on writing convention. ICE was validated on LMSYS/ShareGPT/WildChat — all "people typing at a chatbot", all sharing conventions — so the bets never looked broken.

  **⚠ FRAMING, and the first two attempts at this entry got it wrong. This is NOT "make it work for the maintainer."** The user is an *existence proof* that out-of-convention writing exists, not the target population. Tuning toward their corpus would be the identical mistake with a different corpus. **We have no idea how any given person writes, and no corpus can tell us** — a writing style is not a distribution you can sample your way out of. The requirement is therefore **invariance**: the same intent, written any way, must produce the same decision. Personal rows are a canary, nothing more.

  **This is not one weird user — the rule is unstable across every population we have.** T2's gate accepts a time expression if the prompt *starts with* one of twelve interrogatives. Firing rate: lmsys 25%, wildchat 14%, sharegpt 13%, personal 2% — **a 10x swing, and 2x between the public corpora alone.** The signal is not absent from the low ones: an interrogative sits in the first eight words of 23% of the personal rows. The rule reads *position 0*, and people write `"so what about comparision to the ground truth"`. It discards 21% of those rows against 10% of the corpus's.

  **⚠ AND THE TRAINED HEAD IS NOT AUTOMATICALLY THE FIX — measured, 2026-07-28.** Firing-rate spread across the four sources: `has "?"` **1.5x**, `interrogative-1st` 10x, `p_temporal>=.85` 8.2x, **`p_ltm>=.5` 16.2x**. The model's outputs swing *more* than the crudest heuristic. That measurement is **confounded** — personal rows genuinely need memory more than one-shot public prompts, so much of `p_ltm`'s spread is real content difference — **and that confound is the point**: firing-rate-by-source cannot separate "different people" from "different meanings", so it is a smell detector, never an acceptance test. Do not swap a heuristic for a head and declare victory.

  **THE ACCEPTANCE TEST — paraphrase invariance, which controls for content by construction.** Build a small **style-variant probe set**: take N prompts of known intent and write each one several ways, holding meaning fixed while varying only form — with and without a question mark, formal vs. `"ok so"` / `"like"` / `"hey"` prefixes, interrogative first vs. buried, capitalised vs. all-lowercase, clean vs. typo'd, terse vs. rambling. **The metric is the decision-flip rate across variants of one prompt.** A rule that flips is measuring typography. **Apply it to the replacement too** — the head has no invariance evidence either, and this set is the only instrument that can produce it. This probe set is a **deliverable of G28** and belongs beside `hard_probes.py` (authored in a script, version-controlled, eval-only forever).

  **The distinction that keeps this actionable — parsers stay, inferences get measured.** `_scan_expressions` turning "march 2025" into a datetime is a **parser**: it converts, and a model would be strictly worse because an invented window silently hides every memory outside it (Track T's standing invariant). But `if "?" in text or first_word in {12 words}` deciding *"is this a question about the past"* is **inference from typography**. Rule: a lexicon that RESOLVES a value may stay; a lexicon that INFERS INTENT must pass the invariance test, and so must whatever replaces it. ⚠ Even the parser has a convention ceiling — 250 of 557 real time-questions ("back when we started", "before the rewrite") match no shape it knows; that half is T5(b)'s, not a parser fix.

### ⚑ WHAT Z1 AND Z2 ACTUALLY ARE — clarified by the user, 2026-08-04

> Written after the G32/a1 evidence run, which is itself the worked example of the Z1 half.

**Z1 = every piece tested IN ISOLATION, on real prompts.** Not a smoke test and not a
tuning-only pass: take actual prompts, drive **one subsystem at a time**, and write down
**every** failure point. Two kinds come out and both get recorded: **bugs** (it does not do
what it says) and **design problems** — the "enum-type" finding, where the code works exactly
as written and the *design* is wrong. The G32/a1 run is the template: harvest what the
component really produces, with the downstream filter removed so the failures stay visible,
then read them. Fix what is fixable in place; log the rest for the fix pass.

**Z2 = the whole system, run as SPOT CHECKS IN BATCHES — not one big experiment.** The
structure borrows from the paper's Experiment 2, but it is **not** "run it all and read the
result at the end". It is: one conversation, a small chosen probe set, read the output, fix
or note, repeat. **Z2 is expected to run MULTIPLE times.** Only after the accumulated problem
list from Z1 + Z2 is in hand does the real fix pass happen — and FINAL comes strictly after
that, on a frozen system.

**Corpus shape — recommendation (asked by the user, 2026-08-04): use the MASSIVE
conversations, and cut the PROBE count instead.**
- Conversation size is what creates the conditions ICE exists for — memory pressure, decay,
  clustering, an accumulated codex, a context budget that actually binds. **A short
  conversation cannot produce a retrieval failure, because everything still fits in the
  window and retrieval changes nothing.** Shrinking the conversation removes the phenomenon
  under test.
- Probe count buys statistical confidence, which is FINAL's job, not Z2's. For *finding
  problems*, five probes against a deep store beat two hundred against a shallow one.
- And probe count is exactly what makes the loop slow, which matters because Z2 runs
  repeatedly. **This session is the evidence**: 300 turns exposed a 68% failure rate. 3,000
  would have said the same thing, four hours later.
- The binding constraint is **reading**: Z2's whole value is a human reading output. Twenty
  outputs is a morning; 1,211 is impossible, which is how Exp 2 shipped with the problem
  unseen.
- ⚠ Two conditions on the small probe set: probes are **chosen, not sampled** — deliberately
  spanning the legs (codex · vector · BM25 · procedural · temporal · clusters) so every
  subsystem is exercised at least once; and the conversation is **held fixed across runs**,
  so repeat runs are comparable and a fix can be seen to have worked.

  ### ⚑ THE PROTOCOL Z2 SHOULD USE — proven on Z1's key verification, 2026-08-11 (user)

  **Z2's shape is "read twenty turns and see what's wrong", which is powerful and
  unstructured, and unstructured is what makes it exhausting and unrepeatable.**
  Z1's ground-truth verification accidentally produced a better shape, it caught
  four real defects in one sitting of ~25 items, and the user asked for it to be
  carried here. It is six rules and they are all about protecting human attention,
  which is the scarcest instrument in this project.

  0. **⚑ IT RUNS ON BOTH HALVES — WHAT WAS RETRIEVED *AND* WHAT THE MODEL
     ANSWERED (user, 2026-08-11).** Not retrieval alone. The two failures are
     independent and only the pair is diagnostic: retrieval can surface exactly
     the right memory and the model can still ignore it or contradict it, and a
     good answer can come out of bad retrieval because the model already knew
     the thing. Judging either alone attributes the fault to the wrong half —
     and "the answer was fine" is precisely how a dead retrieval leg survives a
     review. Each sampled turn therefore carries **two** verdicts: *was the
     evidence there* and *did the answer use it*.
  1. **ONE question per artifact, answerable yes/no.** Not a rubric, not a 1–5
     score. Z1's was *"could someone answer Q using only the turns shown?"*.
     Z2's lanes each get their own: did the right memory come back · did the
     summary drop anything load-bearing · is this extracted fact true · does the
     assembled prompt read as usable context · **did the model's answer actually
     use the retrieved memory, or answer around it**.
  2. **Silence means correct — only failures are written down.** Recording 25
     "fine"s is 25 chances to stop paying attention.
  3. **State what is NOT being judged**, explicitly, next to the question. Z1's
     sample said: not whether the answer is *good*, not whether these are the
     *only* supporting turns. Without that line the reviewer invents a stricter
     standard and the number stops meaning one thing.
  4. **⚑ CENTRE THE EXCERPT ON THE EVIDENCE, never on the artifact's opening.**
     The first draft showed each turn's first 300 characters; a 2,000-character
     turn with the supporting sentence at 800 would have been rejected as wrong.
     **This one rule is the difference between measuring the system and
     measuring the excerpt window.**
  5. **A STOP RULE, stated up front** (Z1's: three failures ends the session).
     Once the verdict is known, further reading buys nothing and the reviewer
     is being asked to work out of duty.
  6. **⚑ REPORT THE BREAKDOWN, NEVER THE AVERAGE — this is what made it worth
     doing.** Z1's aggregate was ~4 failures in 25, which reads as "mostly
     fine". Split by conversation it was **4 of 6 on one conversation** against
     1 of 11 on another, which is a different finding entirely and named the
     cause (uniform vocabulary in a single-subject conversation defeats a
     rarity-based shortlist). ⇒ **stratify the sample and publish the split.**
     Same principle C16 already handed Z2 for tokens ("median and win-rate,
     never a mean of means").

  **And the finding that came out of it, which Z2 inherits:** the human found a
  *class* of probe the machine could not — questions asking for **synthesis**
  ("walk me through all of it") have **no single answer-bearing turn by nature**,
  so any metric keyed on one is meaningless for them. Z2 must classify what it
  is judging before it judges it; see [G40](#g40), which owns the missing
  `probe_type`.
